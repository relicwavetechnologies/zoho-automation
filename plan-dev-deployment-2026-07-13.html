Isolation boundaries

The production compose files hard-code the divo_divo-internal network and divo_divo_postgres_data volume. Dev must have different names and data.

Filesystem

/opt/divo-dev

Separate compose, env file, logs, image tags, and rollback manifest. Never write over /opt/divo.

Data

divo-dev-postgres

New database, credentials, and Docker volume. No production DATABASE_URL.

Network

divo-dev-internal

Separate network and Redis volumes. Postgres/Redis stay private; app ports bind to loopback.

Edge

One dev hostname

For example dev.divo.example.com: Nginx sends /api to backend and the rest to admin.

Secrets

GitHub development Environment

Environment-scoped deploy key and dev env file. Production secrets are unavailable here.

OAuth / SaaS

Separate callbacks

Use dev OAuth apps or registered dev redirects. Do not copy production integration tokens to dev.

Workflow shape

Keep production deployment unchanged. Add a separate dev deploy workflow and expand CI to validate dev before it can deploy.

# ci.yml
on:
  pull_request:
    branches: [main, dev]
  push:
    branches: [main, dev]

# deploy-dev.yml
on:
  workflow_run:
    workflows: [CI]
    branches: [dev]
    types: [completed]

concurrency:
  group: deploy-development
  cancel-in-progress: true

jobs:
  deploy:
    if: github.event.workflow_run.conclusion == 'success'
    environment: development
    # images: ghcr.io/.../backend:dev-<sha>
    # target: /opt/divo-dev
    # schema: prisma migrate deploy
    # smoke: loopback + dev HTTPS hostname

Deploy the successful CI run’s head_sha. Do not deploy latest; rollback must select a known previous SHA.

Risks and gaps

VM credential is not valid

The supplied root password was attempted once via SSH and rejected. I stopped there—no retries, no changes. We need the correct SSH user/key or corrected password before inspecting the host.

Nginx is already host-owned

The public IP returns Nginx 404 on HTTP and HTTPS. Do not expose 3001/8081 publicly; add a deliberate virtual host and TLS certificate after reviewing existing config.

Admin relies on outer API routing

The admin image serves static files only. Its empty API base requires host Nginx to proxy /api to backend. Dev must implement this explicitly.

Production deploy uses db push

For a fresh dev DB, use checked-in migrations with prisma migrate deploy. Snapshot the dev volume before any reset.

Safe next steps

Verify VM access

Provide a working SSH key/user or corrected credential. Inspect firewall, Docker, Nginx vhosts, active stacks, disk, and RAM read-only.

Choose the dev hostname

Create DNS for one HTTPS hostname. It keeps admin’s relative /api calls same-origin and gives OAuth a clear callback base.

Create isolated runtime files

Add dev compose, env template, Nginx vhost, and a non-root divo-deploy user with a restricted SSH key.

Configure GitHub Environment

Add only development secrets and restrict its deployment branches to dev.

Prove deploy and rollback

Push a no-op dev commit; verify SHA images, HTTPS health, migration, admin login, and rollback to the previous SHA.

Evidence and alternatives

Inspected: .github/workflows/ci.yml, .github/workflows/deploy.yml, both Compose files, admin/nginx.conf, both Dockerfiles, environment template, and Prisma migrations.

  • Recommended: GitHub-hosted CI + GHCR + SSH deployment to an isolated Compose stack. It extends the current pattern with the least operational change.
  • Alternative: self-hosted runner on the VPS. Fewer SSH secrets but a compromised workflow can execute directly on the server.
  • Alternative: separate dev VPS. Stronger blast radius but higher cost; preferable if dev will carry realistic customer data.

GitHub’s workflow_run jobs can access secrets even when the upstream workflow cannot; therefore this job must only deploy trusted dev code. GitHub Environments scope secrets and branch rules to the deployment job.
