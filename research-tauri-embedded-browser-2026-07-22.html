Render a browser inside Divo without turning Divo into an unsafe browser.

The best in-scope implementation is Tauri v2 native multiwebview: Divo’s trusted local UI remains one webview, while every page is rendered in an isolated child webview backed by WebView2 on Windows and WKWebView on macOS.

Recommendation: build a restricted, first-party/approved-site browser panel first. Do not build a general browser or bolt CEF onto Jan now. Arbitrary public URLs should open in the user’s system browser until a separate browser-grade security and compatibility program justifies Chromium/CEF.
Decision at a glance

Native child webviews are right; an iframe or a CEF detour is not.

Engine

Trusted Divo chrome; untrusted remote content.

Current blocker
RBAC scope

Current main window permissions are too broad for a remote child view.

API maturity
Unstable

Child webviews require Tauri’s unstable feature. Pin and isolate it.

Verified locally in Jan/Divo: jan/src-tauri/capabilities/default.json and desktop.json apply broad shell/native permissions to windows: ["main"] and also define a broad remote http://* rule. A child page in main must not be introduced before capabilities are moved to the trusted local webview label and remote access is removed or tightly dev-scoped.
The implementation shape

One native window. Two hard trust zones.

Native Tauri window “main”
├── trusted Divo UI webview (“main-ui” / existing trusted main view)
│   ├── chat, browser tabs, URL field, navigation controls
│   ├── the only webview with Divo capabilities and Tauri IPC
│   └── invokes typed Rust commands; never handles page DOM
└── browser-tab-<UUID> native child webview
    ├── WebviewUrl::External(https://…)
    ├── no remote capability, no initialization script, no bridge
    ├── Rust-owned navigation / popup / download policy
    └── sanitized URL, title, load state → event → trusted Divo UI

Windows renderer: WebView2 (Chromium)   ·   macOS renderer: WKWebView (WebKit)
Why this is the correct boundary.
External content cannot access Divo sessions, filesystem, MCP, tools, store, shell, or custom commands. Rust is the sole authority over the view’s lifecycle and every URL transition.
Native layering constraint.
A child webview sits above HTML composition. Normal React z-index, rounded clipping, command palettes and modals cannot overlay it. Keep chrome outside its rectangle; hide or park it while a modal is open.

Divo implementation design

Build a browser panel behind a small Rust adapter.

  1. Fix the security boundary first. Scope privileged capabilities to the trusted local webview (for example webviews: ["main-ui"]), remove broad remote grants, and make browser-tab-* match no capability. Register custom commands with explicit authority. Prove a remote page cannot invoke any command.
  2. Enable and pin the multiwebview API. Add Tauri’s unstable feature deliberately, lock the Tauri/WRY version, and put all unstable API use in one browser_surface Rust module. Jan is currently on Tauri 2.8.5 without that feature.
  3. Start with one approved-site view. Have the trusted UI request a typed create/navigate/resize/show/hide/close operation. Rust generates the tab UUID and label; the renderer receives only safe state events. No arbitrary JavaScript evaluation or page bridge.
  4. Install a real URL and popup policy. Parse URLs in Rust. Permit HTTPS; make HTTP an explicit policy decision; reject file:, data:, javascript:, Tauri/custom schemes, credentials in URLs, control characters and oversized inputs. Deny popups by default; send user-approved HTTPS popups into a managed tab. Use the system browser for OAuth unless a provider has been tested and approved.
  5. Make geometry native-aware. The local React layout reports one logical-pixel content rectangle through a debounced ResizeObserver. Rust validates it and resizes/positions the child. Reapply after window resize, DPI/scale changes, sidebar/composer changes and fullscreen. Use native menus or temporary native windows for controls that must appear over the page.
  6. Add a bounded tab manager only after the one-tab spike passes. Keep roughly 4–6 warm views maximum. Park hidden views, then hibernate least-recently-used views by destroying the native renderer while retaining safe URL/title metadata. Never claim unsaved page state survives hibernation.
  7. Add storage and transfers deliberately. One Divo-user browser profile supports SSO across normal tabs; a nonpersistent profile supports private tabs. On Windows use a dedicated writable WebView2 user-data directory; on macOS use the default persistent data store with a macOS-14+ named-store enhancement only if needed. V1 denies downloads and sensitive device permissions; later transfers stage files privately and require an explicit Save As action.
Cross-platform rules

Where implementations usually fail

Windows / WebView2

  • Create/destroy child views only from async commands or a separate thread; synchronous creation can deadlock.
  • Keep the host opaque and test at 100%, 125%, 150% and multi-monitor DPI.
  • Use a single user-data folder/profile per Divo user. Too many folders cause extra browser process collections and memory overhead.
  • Do not treat Windows-only extensions, browser args or WebView2 COM interception as cross-platform features.

macOS / WKWebView

  • Test Intel and Apple Silicon packaged builds; WebKit compatibility follows the installed macOS version, not Windows Chromium.
  • Use the shared persistent store for normal tabs and a nonpersistent store for private tabs. Named persistent stores need macOS 14+.
  • Expect a different set of OAuth, media, WebRTC, storage and popup behaviours. Treat system-browser handoff as a first-class path.
  • Divo already enables macos-private-api; the browser panel should not add further private API dependence.
Acceptance gates

What must be true before Divo enables it.

V1 product boundary: show approved company SaaS domains inside Divo; open all other public URLs in the default browser. This gives a useful integrated surface without making a false browser-security claim.
  1. Security gate: packaged test pages on http and https cannot invoke commands, access plugins, create privileged webviews, access local storage or receive a custom initialization script.
  2. Behaviour gate: test redirects, single-page-app URL/title changes, back/forward/reload, target=_blank, downloads, file upload, text selection, clipboard, fullscreen and modal layering.
  3. Identity gate: test company SSO, Microsoft/Google OAuth external-browser fallback, third-party cookies and logout/clear-profile semantics.
  4. Platform gate: run packaged builds on Windows 10/11 plus the oldest supported/current macOS on Intel and Apple Silicon; include scaling, sleep/resume and multi-monitor tests.
  5. Reliability gate: run 1, 5, 10 and 15-tab memory tests; rapid create/switch/close/resize tests; deliberate renderer failure and cold-tab restoration.
