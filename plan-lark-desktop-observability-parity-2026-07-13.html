Codebase evidence

What the audit found

The issue is broader than a missing key. The current implementation shares identity and permissions, but forks inference, metering, conversation indexing, and operational controls.

01

Direct provider bypass

Lark’s supervisor receives a startup-created AI SDK model. DeepSeek resolution reads the server environment, while desktop uses the authenticated backend proxy and encrypted key store.

02

False-green failure

A streamed model error is logged, but the supervisor may fall back to “Done.” The run can complete instead of failing, weakening error-rate and incident reporting.

03

Token ledger hole

The Lark orchestration path never records model usage. Its run header exists, but turns, tokens and cost remain empty in AI Ops.

04

Model controls disagree

Company settings are written to Company, while startup inference reads a globally unique model target. Admin-visible company policy is not necessarily runtime policy.

05

Conversation index gap

Desktop and AirNote upsert RuntimeConversation. Normal Lark messages do not; Lark creates one only opportunistically during approval flows.

06

Two run authorities

ExecutionRun powers AI Ops, while RuntimeRun exists separately. Parity should consolidate semantics around the former, not dual-write two competing run ledgers.

Recommended architecture

Adapters at the edges, authority in the middle

Desktop and Lark do not need identical orchestration runtimes. They need identical policy and telemetry contracts.

Channel adapters

  • Desktop/Pi HTTP + WebSocket
  • Lark webhook + cards
  • AirNote SSE
  • Emit canonical identity + channel context
→

Backend authority

  • InferenceGateway — model/key resolution
  • InferencePolicy — block/model/rate/budget
  • ObservabilityRecorder — runs, spans, usage, audits
  • PermissionService + ToolRegistry — existing authority
  • ApprovalGate — shared state, native presentation
→

Operational read model

  • ExecutionRun + events + steps
  • AiTokenUsage linked to run/span
  • InferenceRequestLog with channel
  • RuntimeConversation as thread index
  • AI Ops, Guardrails, alerts
Implementation roadmap

Six reversible phases

Effort is relative for one backend-focused engineer plus admin UI support. Each phase is independently testable and feature-flagged.

Ship

  • Document canonical run/event/model-span contracts.
  • Make ExecutionRun monitoring authority.
  • Define channel enum and entrypoint derivation.
  • Define provider/model resolution precedence.

Exit gate

  • No ambiguous owner for run status, usage or budget.
  • Golden fixture for one desktop and one Lark turn.
  • Rollback: documentation/types only.

Ship

  • Correct entrypoint per channel.
  • Unify event taxonomy and correlation envelope.
  • Convert streamed model errors into failed spans/runs.
  • Guarantee one terminal run status.

Exit gate

  • Missing-key Lark test ends failed, never “Done.”
  • Admin run detail shows channel and exact failure.
  • Rollback behind telemetry-v2 flag.

Ship

  • Generalize DeepSeek-only key store by provider.
  • Add internal InferenceGateway.
  • Make desktop HTTP proxy a thin adapter.
  • Route Lark supervisor and agent model resolution through it.
  • Resolve company model settings per request, not startup.

Exit gate

  • Same blocked user is denied on desktop and Lark.
  • Same budget bucket sees both channels.
  • No provider key reaches clients or logs.

Ship

  • Instrument supervisor, specialists, fast path, summary and synthesis.
  • Write usage linked to executionRunId.
  • Add provider-neutral request log with channel.
  • Add dated provider/model pricing catalog.

Exit gate

  • Run total reconciles to sum of model spans.
  • Lark tokens and cost appear with channel=lark.
  • Dual-write comparison stays within agreed tolerance.

Ship

  • Upsert RuntimeConversation for normal Lark traffic.
  • Link ExecutionRun to conversation without creating a second run authority.
  • Link approvals and delivery events to the same run.
  • Persist Lark message/card IDs as channel references.

Exit gate

  • One admin trace follows webhook → model → tool → card.
  • Approval resume continues the original correlation chain.
  • Channel deletion/retention behavior tested.

Ship

  • Channel filters on cost, tokens, latency and denials.
  • Member page shows cross-channel spend and limits.
  • Guardrails feed labels desktop/Lark.
  • Alerts for error spikes, empty replies, missing usage and latency.

Exit gate

  • Shadow dashboard reconciles desktop + Lark totals.
  • Canary one company, then staged rollout.
  • Rollback keeps legacy Lark inference flag available briefly.
Risks and open decisions

What can still go wrong

The plan is high confidence, but these decisions should be explicit before implementation.

Double counting during migration

Proxy-owned usage and SDK instrumentation can both write the same desktop call.

Attach a deterministic inference request ID; dual-write to a shadow table first and enforce uniqueness before cutover.

Policy changes alter active runs

Per-request resolution is correct, but a long run may see a model/key change between steps.

Snapshot effective policy and provider selection onto the run; define whether changes apply next call or next run.

Provider usage shapes differ

DeepSeek, OpenAI and Google expose different cache and reasoning-token fields.

Normalize into a canonical usage type while retaining raw sanitized provider usage for reconciliation.

PI and backend have different orchestration

Forcing identical traces would erase useful channel/runtime differences.

Standardize semantic spans and required fields, not internal step counts or UI presentation.

Pricing silently undercounts unknown models

The current fallback uses the cheapest DeepSeek tier, which is unsafe for OpenAI/Google reporting.

Version rates by provider/model/effective date and mark unknown costs “unpriced,” never cheap-default.

Retention and privacy

Lark group context and tool outputs may contain broader company data than desktop threads.

Keep payload redaction, role-scoped reads, short trace-detail retention, and long-lived aggregate usage only.

Alternative A — make Lark call /api/llm over loopback
Useful as a short spike, but not the target. It adds synthetic member authentication, an internal HTTP hop and weak agent/span attribution. Prefer a shared application service with HTTP as one adapter.
Alternative B — add DEEPSEEK_API_KEY to the backend
Fixes the immediate exception only. It preserves the split key authority, skips member guardrails, leaves Lark usage invisible and makes admin controls misleading. Reject as a final design.
