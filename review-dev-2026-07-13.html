What the log proves

A zero-model local server starts anyway

The supplied startup log records backend/Divo requests succeeding, then local Llama.cpp backend detection and a local router start. It reports Available models (0) and still starts a llama-server process. That is unused work, extra startup failure surface, and an unnecessary local cache.

This is not a theory about unused code: the released ARM build is executing it on each launch with no local model loaded.

Remove Llama.cpp router, extension, and model-download flow

src-tauri/src/lib.rs registers the plugin and shutdown handlers; the attached log proves it launches despite zero models. Hub/model-provider, local download, hardware, and router error UI are all Jan-only product surface.

- .plugin(tauri_plugin_llamacpp::init())
- llama router lifecycle / exit cleanup

- Hub local-model download and hardware UI

The 78 MB Llama.cpp folder is runtime data, not 78 MB inside the DMG. Removing this path prevents it being downloaded and started; measure the app-binary saving separately.

Remove the bundled jan-cli binary and its auto-install

Its own command description is “Serve local AI models … no cloud required.” It is built into the app, shipped under resources, and automatically installed onto the user’s PATH at startup. That conflicts with Divo’s backend-only model architecture.

- core::setup::setup_jan_cli(...)
- install_jan_cli / uninstall_jan_cli commands

High confidencecleanup

Stop shipping local-model extension installers

After inference is removed, the Llama.cpp and MLX installer archives must go too; otherwise an old Jan path can be reintroduced later. Their bytes are small, but leaving them is misleading and weakens the product boundary.

- janhq-llamacpp-extension-*.tgz
- janhq-mlx-extension-*.tgz
# remove their build/test scripts at the same time
Needs product decisionpotential −49 MB

Do not remove uv yet

uv is 49 MB, but it supports Jan’s generic local MCP servers, including mcp-server-fetch. Divo already instructs Pi to use backend research for company work, so this is a strong next candidate—but local MCP/browser workflows still reference it.

Safe only after the product explicitly disables generic local MCP servers or migrates their supported use cases to backend-owned capabilities.

Needs product decisionpotential −40 MB

Do not remove bundled Lark CLI yet

The app actively bootstraps a private lark-cli wrapper into Pi’s PATH and has a UI for local Lark connection setup. That is not local model code, and it remains a live desktop feature even if backend Lark is preferred for company work.

It becomes removable only after local/personal Lark is deliberately removed and every route uses the backend gateway.

Needs tracingavoid accidental attachment regression

Keep local RAG/vector plugins for this first cut

They are wired into attachment ingestion and RAG tools in the current web app. They may be obsolete for Divo’s backend-owned RAG, but deleting them without first redirecting attachments to the backend would break document handling.

Treat this as phase 2: define the backend document/attachment contract, migrate it, then remove local embedding/vector code.

Keep60 MB but required

Keep Bun and the core Pi runtime

Bun is the process that runs bundled Pi. Pi is the Divo agent loop that invokes the constrained backend gateway. Neither is a local model runtime. Removing them would remove chat execution, not just Jan’s inference stack.

+ resources/pi                               410 MB

Low-risk implementation order

One disciplined removal PR

Introduce a Divo runtime feature boundary.
Make Pi/backend the only model path. Remove the startup call that initializes model providers and any zero-model router start.
Remove MLX and Llama.cpp together.
Delete their plugins, resources, build steps, extension packages, routes, and tests in the same PR so no orphaned entry point survives.
Remove jan-cli and its PATH installer.
Also remove user-facing local-model CLI settings/help. Do not leave a dormant executable in the bundle.
Build ARM and Intel, then compare artifacts.
Smoke test first chat, attachment OCR, Divo gateway invocation, OAuth reconnect, and quit/relaunch. Record DMG and installed-app deltas.
Only then evaluate Pi, uv, Lark, and local RAG.
Those are separate product capability decisions, not cleanup of an unused model runtime.
Guardrails

What not to do

  • Do not delete Pi just because it is large. It runs the actual agent loop.
  • Do not delete local RAG/vector support before attachment handling is explicitly migrated to the backend.
  • Do not remove uv or Lark CLI until their supported local workflows are turned off by product decision.
  • Do not strip arbitrary provider packages from Pi’s third-party node_modules. That needs a reproducible slim distribution and Pi smoke tests.
  • Do not claim a 78 MB DMG reduction for Llama.cpp: that 78 MB is currently downloaded runtime state, not bundled DMG content.
The first removal phase has an immediate, defensible direct bundle target of at least 61.3 MB on ARM, plus elimination of the unwanted local-server startup and 78 MB local cache creation.

Evidence inspected: jan/src-tauri/src/lib.rs, jan/src-tauri/Cargo.toml, macOS Tauri bundle configs, jan/package.json, Pi runtime/vendor scripts, local Lark runtime, installed ARM app layout, and the supplied startup log. No production code was changed by this audit.
