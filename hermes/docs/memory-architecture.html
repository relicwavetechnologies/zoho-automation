Divo / Hermes · architecture brief

Memory & RAG, and the multi-tenant blind spot

Hermes shipped as a single-user assistant. Divo runs it multi-tenant (many companies, many users each). The memory layer was ported across — but only half of it learned about tenants.

01 — the landscape

There is no “RAG.” There are two memory systems.

No self-hosted vector DB (no Qdrant/pgvector), no document-ingestion pipeline. “Memory” here means conversational facts the agent learns — not retrieval over uploaded documents. web_search / web_extract are live-web tools, fully separate.

always on

① Built-in file memory

Plain Markdown files: MEMORY.md (facts) + USER.md (profile). No embeddings, no search — a frozen snapshot injected into the system prompt at session start. Company-scoped by directory.

tools/memory_tool.py · get_memory_dir() L82

at most one active

② External memory plugin

A cloud “brain” that does semantic recall, fact-extraction & profiles: mem0, supermemory, hindsight, honcho (cloud) or holographic (local SQLite). Embeddings computed server-side. Not company-scoped.

agent/memory_manager.py · one external + builtin, L258–280

Selected via memory.provider in config.yaml. The built-in always runs; the manager allows one external alongside it.

02 — the pipeline

How a memory flows · click a stage

Every turn runs a tiny write→store loop in the background, and a read happens just before the model is called.

WRITE ↑

1 · Capture

After each turn, the turn is handed to memory — plus an explicit memory() tool and a session-end pass.

  • sync_all(user, assistant) fires after every turn — non-blocking — run_agent.py L2917
  • on_session_end(messages) lets cloud providers ingest the full transcript — L2833
  • Agent can also call the memory tool (add / replace / remove) → mirrored to the external provider
  • External writes are extracted: the cloud service runs an LLM to distill facts, not store raw chat
→
STORE ◇

2 · Persist

Each provider stashes it differently — file, local SQLite, or a cloud vector store with server-side embeddings.

  • Built-in → append to MEMORY.md / USER.md (no vectors)
  • mem0 / supermemory / honcho / hindsight → cloud, embedded & indexed server-side
  • holographic → local SQLite with HRR phase-vectors + FTS5
  • ⚠ the partition key chosen here is where tenant isolation is won or lost
→
READ ↓

3 · Recall

Before each model call, relevant memory is fetched and injected as a fenced <memory-context> block.

  • prefetch_all(query) runs once per turn (not per tool-call) — conversation_loop.py L783
  • Result wrapped in <memory-context> & marked “recalled, NOT new user input” — memory_manager.py L227
  • A streaming scrubber strips those tags so the user never sees them
  • Agent may also pull on demand: mem0_search, supermemory_search, hindsight_recall…

prefetch is a semantic search for cloud providers (embed the query → top-k), or a frozen snapshot for the built-in file memory.

05 — the fix

Fold the company into the partition key

The enterprise identity already reaches each provider. Each provider needs ~3 lines to use it.

What to change

  • mem0 — read kwargs["company_id"] in initialize(); add it to _read_filters() & _write_filters()
  • supermemory — extend container_tag with a {company} segment
  • hindsight — add a {company} placeholder; default bank_id = {company}-{user}
  • honcho — namespace the session_key/peer by company
  • document company_id / company_user_id in the MemoryProvider ABC kwargs
  • add a per-provider isolation regression test (two companies, same user id → no cross-read)

The pattern (mem0)

def initialize(self, session_id, **kwargs):
    self._user_id = kwargs.get("user_id") or "hermes-user"
    self._company_id = kwargs.get("company_id")

def _read_filters(self):
    f = {"user_id": self._user_id}
    if self._company_id:
        f["company_id"] = self._company_id
    return f

Mirror the built-in tool’s proven pattern — it already does exactly this with hashed directories.
