Reuse Lark’s API stack.
Keep identity and control in Divo.

You do not need to rebuild Lark API calls from scratch. The official Node SDK is the production-grade transport. Your missing work is a consistent connection + token + RBAC routing layer around the Lark tools that already exist in Divo.

Scope: user OAuth, open source implementations, current Divo coverage•Confidence: high
Decision

The direct answer

Adopt @larksuiteoapi/node-sdk inside the backend and make every Lark action resolve a Divo-owned, encrypted user connection. Do not deploy Lark’s official MCP as your shared production gateway: its own documentation says streamable OAuth currently supports localhost only. Keep the current Divo gateway as the sole policy, audit, approval, and connection authority.

Official OAuth model

Use the user’s Lark identity for user-owned data.

DesktopUser selects a Lark connection and grants consent.
→

→
Encrypted connection vaultStores user token, rotated refresh token, expiry, Lark open ID, and grant metadata.
→

Required behavior

  • Request only the needed scopes plus offline_access when Divo must refresh in the background.
  • Use an exact allow-listed callback URI; Lark’s authorization code is short-lived and single-use.
  • Persist the new refresh token atomically on every refresh: Lark refresh tokens rotate and cannot be treated as reusable static credentials.
  • Use user_access_token for private/user-owned resources; tenant tokens are an app/tenant identity, not a replacement for personal consent.
Open source assessment

What to reuse — and where it belongs.

Official Node SDK

Adopt

Typed, semantic Node client with a first-class withUserAccessToken request option and Lark international domain support.

Fit: production transport in Divo’s infrastructure adapters. It removes HTTP boilerplate; it does not replace your policy layer.

Official Lark OpenAPI MCP

Reference / prototype only

Useful for checking API/tool coverage and validating operations during development. It demonstrates user-token mode clearly.

Not the runtime: its published streamable OAuth limitation is localhost-only, which rules out Divo’s shared cloud connection model.

Official Lark CLI

Reference / test harness

Broad, actively maintained command surface across messaging, docs, Base, sheets, calendar, mail, tasks, meetings, and more.

Not the runtime: it manages local token/config state; Divo requires server-side encrypted per-connection records and company grants.

Legacy Node SDK

Avoid

larksuite/oapi-sdk-nodejs is the older package. The official organization directs users to the current node-sdk. Do not start new work on it.

Community signal worth designing for

Confirmed concern

The official CLI has a public multi-account/profile discussion. That is the exact problem Divo must solve at the product layer: a member may hold several Lark connections, and a company may grant colleagues access to a selected connection without ever sharing token material.

Recommended Divo build

Build the small layer that open source cannot own for you.

Phase 1 — normalize user-token execution

Extract the existing Tasks token resolver into one Lark connection-token service. Pass it into each existing Lark tool client factory. This is the smallest change that makes requests act as the connected user consistently.

Phase 2 — move Lark into the generic connection registry

Add provider lark alongside Google/Zoho/Canva. One connection record per OAuth authorization, labelled by the member, tenant, and Lark identity. Migrate or bridge the current Lark auth-link repository; do not create a second competing token store.

Phase 3 — grants and selection

At gateway invocation, resolve connectionId → owner/share grant → Lark token. Enforce department role, scope-to-operation mapping, approval policy, and audit record before the SDK call. A share gives permission to use, never permission to view/export the token.

Phase 4 — expand safely

Use the official MCP and CLI as capability inventories/tests, then add high-value Lark surfaces behind stable Divo tool contracts. Avoid exposing a raw “call any Lark API” tool to the agent.

Guardrails

What must not change.

Divo stays the authority

  • Pi/Desktop never receives Lark app secrets, access tokens, or refresh tokens.
  • The Lark SDK is an infrastructure dependency, not an alternate policy system.
  • One constrained Divo gateway remains the agent-facing surface.
  • Connection sharing is an explicit DB grant, independently auditable and revocable.

Prevent the likely failures

  • Do not fall back from user token to tenant token silently for private data.
  • Never put a refresh token in desktop config, logs, tool arguments, or MCP environment variables.
  • Fail closed when a user token has expired and refresh cannot be persisted.
  • Validate Lark scope, Divo RBAC, connection sharing, and action approval as separate checks.
Bottom line: Yes, reuse exists in detail. Use Lark’s official Node SDK for every actual OpenAPI request and use its MCP/CLI repositories as live reference implementations. But do not outsource your connection management to their MCP: Divo’s security model requires your backend to retain per-user encrypted OAuth records, multi-account selection, sharing grants, RBAC, HITL, and auditing.
