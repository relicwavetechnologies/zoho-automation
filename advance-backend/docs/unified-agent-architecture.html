DeepSeek V4 Flash is 20x cheaper than Claude Sonnet and handles tool calling reliably. The multi-agent pattern was designed for weaker models that couldn't handle many tools. With a strong, cheap model, the delegation overhead (extra LLM calls, context rebuilding, lost conversation state) costs more than it saves.

The arbitrage: A single DeepSeek V4 Flash call with 16 tools costs ~$0.003. The current multi-agent flow makes 3-5 calls costing ~$0.004-0.008 total — but with 3-5x the latency and context-switching overhead. Switching to single-agent saves tokens AND time.

How Skills Work (Progressive Context Loading)

This is the same pattern used by Claude Code, Microsoft Agent Framework, and Google ADK. Three levels:

Skill Loading: 3-Level Progressive Disclosure
L1: Skill Catalogalways in context

~100 tokens per skill
Name + one-line description
5 skills = 500 tokens

~1000-2500 tokens per tool

Loaded alongside L2

  filters: { customer_name?,

    status?, ... }
  page?: number

})
Why skills solve domain speciality: Each skill file contains the concentrated expertise that today lives in agent runner system prompts (lark.prompt.ts, zoho.prompt.ts, etc.). The brain doesn't need to know Zoho date formatting rules until it encounters a Zoho task. Skills load that expertise on demand — same quality, 80% fewer tokens on non-Zoho requests.

The Two Meta-Tools

1. discover_skill — Intent → Skill Matching

// Brain calls this when it needs domain expertise
discover_skill({ query: "send email to shivam about Q2 report" })

// Returns: skill instructions + tool schemas loaded into context
→ {
    skill: "google",
    instructions: "Gmail composition rules: always include subject...",
    tools: ["googleGmail", "googleDrive", "googleCalendar"],
    schemas: { googleGmail: { op: "send", to: string, ... } }
  }

// Brain now has everything it needs to call the tool directly
call_tool({ toolId: "googleGmail", args: { op: "send", to: "shivam@...", subject: "Q2 Report", body: "..." } })

2. call_tool — Universal Tool Executor

// ONE tool definition exposed to the LLM
call_tool({
  toolId: "googleGmail",      // which tool to invoke
  args: {                     // validated against the tool's Zod schema
    op: "send",
    to: "shivam@emiactech.com",
    subject: "Q2 Finance Report",
    body: "Hi Shivam, ..."
  }
})

// Backend flow:
// 1. Look up tool by ID in ToolRegistry
// 2. Validate args against tool.argsSchema (existing Zod schemas!)
// 3. Run permission check (existing RBAC!)
// 4. Run approval gate if needed (existing HITL!)
// 5. Execute tool
// 6. Return result to LLM
Key insight: call_tool reuses 100% of existing infrastructure — ToolRegistry, Zod schemas, permission checks, approval gates, tool execution. The only new code is the thin dispatcher that maps toolId → tool object.

Each company gets a skill set — a curated list of skills relevant to their domain. The brain is always the same. Skills are the specialization layer.

Skills vs Agents for domain expertise:
  • Agent approach: Each domain = new agent file + runner + prompt + seed script + 2-4 extra LLM calls. Agents can't see each other's results.
  • Skill approach: Each domain = one skill file with instructions + tool mappings. Brain loads it on demand. Brain sees ALL results in one context. Adding a new domain is a text file, not code.

Request Flow: Step by Step

Example: "Show me overdue invoices and create a Lark task for follow-up"
User: "Show me overdue invoices and create a Lark task for follow-up"

Brain (step 1): This needs Zoho + Lark domains.
  → calls discover_skill({ query: "overdue invoices zoho" })
  → Zoho skill loaded: instructions + zohoBooks schema

  → calls discover_skill({ query: "create lark task" })
  → Lark skill loaded: instructions + larkTask schema

Brain (step 2): Now I have the schemas. Execute:
  → calls call_tool({ toolId: "zohoBooks", args: { op: "list_invoices", filters: { status: "overdue" } } })
  → Backend validates args → checks permissions → executes → returns 5 overdue invoices

Brain (step 3): Got invoices. Now create the task:
  → calls call_tool({ toolId: "larkTask", args: { op: "create", title: "Follow up on 5 overdue invoices", ... } })
  → Backend validates → approval gate (if needed) → executes → task created

Brain (step 4): Synthesize response:
  → "Found 5 overdue invoices totaling ₹4,23,000. Created a follow-up task in Lark assigned to you."

Total: 1 LLM call with 4 tool invocations. No delegation. No context loss.

Implementation Plan

1
Build SkillRegistry + skill files
~4 hours
  • Create src/application/skills/ directory
  • Define Skill interface: { id, name, description, instructions, toolIds, schema? }
  • Build SkillRegistry that loads from skills/*.skill.ts files
  • Extract domain expertise from existing agent prompts into skill files:
    • lark.skill.ts ← from lark.prompt.ts + tool schemas
    • google.skill.ts ← from google.prompt.ts + tool schemas
    • zoho.skill.ts ← from zoho.prompt.ts + tool schemas
    • research.skill.ts ← from context.prompt.ts + tool schemas
2
Build discover_skill + call_tool meta-tools
~3 hours
  • discover_skill: Takes a query, returns matching skill instructions + tool schemas as a string injected into the conversation
  • call_tool: Takes { toolId, args }, looks up tool in ToolRegistry, validates with Zod schema, runs permission + approval checks, executes, returns result
  • Both are Vercel AI SDK dynamicTool instances — same adapter pattern as existing tools
3
Write the Brain system prompt
~2 hours
  • Single focused system prompt: identity, behavior rules, skill catalog
  • No domain-specific instructions in the base prompt — those come from skills
  • Include the L1 skill catalog (names + descriptions, ~500 tokens)
  • Clear instructions: "call discover_skill before using a domain you haven't loaded yet"
4
Wire into supervisor-think.ts (behind flag)
~2 hours
  • Add UNIFIED_AGENT_MODE env flag
  • When enabled, supervisor-think gives Brain: discover_skill + call_tool + orchestration tools
  • When disabled, falls back to existing multi-agent delegation
  • Both paths coexist — zero risk to production
5
Test with harness + compare quality
~2 hours
  • Run same prompts through both paths, compare: tokens, latency, answer quality
  • Test edge cases: multi-domain requests, Hinglish, scheduling, HITL flows
  • Measure DeepSeek's tool selection accuracy with 2+16 tools vs 4+5 tools
Total estimated effort: ~13 hours. Most is extraction (moving existing prompt content into skill files) and the thin meta-tool layer. Zero changes to tool implementations, RBAC, HITL, or infrastructure.
