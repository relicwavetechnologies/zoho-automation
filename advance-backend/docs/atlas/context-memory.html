Desktop architecture

Context & memory that stays light all day

Desktop users may leave Divo open for weeks. The system must preserve full history, keep scrolling smooth, and still guarantee the Mac app never grows without bound. The answer is three separate planes: durable DB history, backend LLM compaction, and a memory-governed renderer cache.

The core rule

Postgres owns the conversation. The renderer owns only the current viewport, current run state, and a small LRU of recently viewed message pages. LLM context is built on the backend from RuntimeConversation, summaries, and retrieval — never from whatever the UI happens to have loaded.

Resource snapshot

Add a native get_resource_snapshot command in src-tauri. It should return total memory, available memory, process RSS, CPU pressure if available, platform, uptime, and timestamp. Browser memory APIs are too inconsistent on WebKit; Rust/sysinfo should be the source of truth.

Memory budget policy

Default numbers should be conservative first; tune after telemetry from real teammate machines.

App RSS target
350-600 MB

About 350 MB on 8 GB Macs, 600 MB on 16 GB+ machines. Emergency eviction starts above target.

Chat store
48-128 MB

min(128MB, max(48MB, available * 3%)). The store never grows without accounting.

Active thread
8-12 MB

Keep the latest message window and current scroll-near pages. Drop far pages first.

Inactive threads
0 full arrays

Summaries only by default. Keep pages for last 2-3 viewed threads only while under budget.

Terminal output
32-60 KB tail

Live UI keeps tail output. Full stdout/stderr is an artifact, not a permanent React object.

Emergency mode
< 1 GB free

Disable prefetch, evict inactive caches, compact activity rows, and pause heavy markdown rendering.

Conversation lifecycle

The user can scroll forever because old data reloads from DB; the app stays light because only nearby data is alive.

1

Send

User message enters the active thread and gets persisted before engine execution.

2

Stream

Only the active run holds live activity, terminal cards, and assistant deltas in memory.

3

Finalize

Final assistant message is saved. Activity rows collapse into compact visible metadata.

4

Compact

Runtime summary updates in background once unsummarized context crosses thresholds.

5

Evict

Renderer drops inactive pages; exact messages are fetched again if the user scrolls back.

Implementation contract

Renderer contract

  • Never store full message arrays for every thread.
  • Keep ThreadSummary[], active message pages, live run state, and small LRU pages only.
  • Every cached object needs an estimated byte cost and last-access timestamp.
  • Switching threads can evict the previous thread after preserving scroll anchor and cursor state.

Backend contract

  • Postgres is the source of truth for visible history and runtime history.
  • Desktop API serves cursor windows, not unbounded histories.
  • LLM context is built from RuntimeConversation, not renderer state.
  • Large payloads are artifacts with previews, never giant permanent chat rows.

Phased build plan

1
Memory telemetry + governor
Add Tauri resource snapshot, renderer MemoryGovernor, cache byte estimates, and eviction tests.
2
Cursor windows + virtualized chat
Replace eager thread hydration with latest/before/after windows and virtualized MessageList anchors.
3
Desktop context profile
Create desktop-specific history and summarization thresholds without touching Lark behavior.
4
Heavy payload artifacting
Move huge terminal/tool outputs to artifacts and keep only previews in UI and prompt context.
5
Observability
Track cache bytes, evictions, loaded pages, memory pressure, prompt allocation, and emergency trims.
Important: compaction solves model-context growth, but not renderer OOM by itself. The Mac app needs a real memory governor even if every conversation is perfectly summarized.
