2. Step-by-Step Breakdown

Step 1: Supervisor Receives Message

1
supervisor.ts:350 — Supervisor calls streamText() with all available agent-tools. The Zoho agent is wrapped as a tool via buildCapabilitiesForAgent() in agent-as-tool.ts. The LLM sees it as agent_zoho_ops (or whatever the agent slug is).

Step 2: Supervisor Delegates to Zoho Agent

2
Supervisor LLM generates a tool call: { toolName: "agent_zoho_ops", input: { task: "..." } }. The Vercel AI SDK executes the tool function, which calls runDynamicAgent().
dynamic-agent.runner.ts:148

Step 3: Zoho Agent Gets Its Tools

3
The agent's tool set is resolved from its toolIds in the database. For the Zoho agent, this includes zohoBooks, zohoCrm, and dataProcessor. Tools are converted to AI SDK format via ai-sdk-adapter.ts:toAISdkTool().

The ZohoReadHook (agent-hook.ts:25) injects additional system prompt telling the LLM:
  • Use dataProcessor for grouping/aggregation/analysis
  • Use zohoBooks for simple lookups
  • Use _balance for outstanding/unpaid amounts

Step 4: Zoho Agent LLM Decides

4
The agent's LLM reads the task + hook guidance and picks a tool. For analytical queries, it calls dataProcessor with a zohoSource and a JS script.
dynamic-agent.runner.ts:148 → generateText()

Step 5: dataProcessor Fetches & Processes

5
5a. Fetch ALL records from Zoho via exhaustive pagination (up to 4000)
data-processor.tool.ts:181 → booksClient.listAllRecords()

5b. Inject synthetic fields on every record:
zoho-books-schema.cache.ts:injectSyntheticFields()
SyntheticSource (bills)Meaning
_amounttotalFull bill value
_totaltotalSame as _amount
_balancebalanceUnpaid/outstanding portion
_datedateBill date
_idbill_idRecord ID
5c. Run the LLM-written JS script in a Node.js VM sandbox (5s timeout, no filesystem/network access)
data-processor.tool.ts:286 → vm.runInContext()

5d. Return processed result (max 50 rows inline, full CSV if requested)

Step 6: Result Flows Back Up

6
dataProcessor returns JSON → Zoho Agent LLM reads it and writes a human reply → Supervisor receives agent result. If only one agent was called, the agent's reply is passed through directly.

5. Known Issues & Complexity

3 code paths for financial queries

zohoBooks tool, dataProcessor tool, and zoho-finance-ops.ts each have their own field resolution logic. A fix in one doesn't propagate to the others.

2 different Zoho API clients

ZohoBooksClientPort (simple, one-page) used by zohoBooks tool. ZohoBooksPaginatedClient (exhaustive) used by dataProcessor and zoho-finance-ops. Same API, different wrappers.

LLM must choose between 2 overlapping tools

The Zoho agent sees both zohoBooks and dataProcessor. The hook tells it "use dataProcessor for analysis" but edge cases are ambiguous. Wrong choice = either missing data (zohoBooks returns 25 records) or unnecessary overhead (dataProcessor fetches 4000 for a simple lookup).

Schema docs duplicated in 4 places

Field information lives in zoho-books-schema.cache.ts, data-processor.tool.ts description, agent-hook.ts guidance, and zoho.prompt.ts. Must update all 4 when a field changes.

What's working well

Synthetic fields (_balance, _total) are verified accurate. Exhaustive pagination handles up to 4000 records. VM sandbox prevents script injection. CSV export with signed URLs works. All 5 test prompts verified against live API with exact matches.
