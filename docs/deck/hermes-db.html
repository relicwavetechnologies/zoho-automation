DB-first transformation

Make Hermes a Divo runtime by anchoring it to one production database.

The first step is not more tools. It is agreeing on the production data shape: Divo Postgres stays the source of truth, Hermes keeps its local SQLite only as a compatibility/runtime cache until the bridge is complete.

Use Divo Postgres as the root DB.

Hermes should not bring a separate production database. Divo already has company, users, memberships, connector auth, tool permissions, runtime conversations, execution events, approvals, and audit tables.

Why this is the first move

decision
  • Multi-company safety starts in the DB. If sessions and tools are not company-bound, later RBAC becomes a patch.
  • Divo already owns the enterprise objects. Reusing them avoids a second user/company system.
  • Hermes becomes the execution engine. It should read/write through Divo contracts when deployed.
  • Tools can move after identity is stable. Zoho, Google, Lark and future connectors need company-owned credentials first.
Current DB reality

Hermes and Divo already overlap. The transformation is mostly a controlled mapping from Hermes' local session model into Divo's company-aware Postgres model.

Schema intersection

Click each area. The point is to reuse the Divo tables that are already enterprise-shaped, then add only the missing Hermes bridge pieces.

Additive schema we should pin down first
01

RuntimeSessionBinding

Maps Hermes `session_id` and gateway session keys to Divo `RuntimeConversation` and current `RuntimeRun`.

02

Generic ConnectorAccount

Normalizes Zoho, Lark, Google and future provider credentials under `companyId` and optional `userId`.

03

ToolAuditEvent

Either extend `StepResult`/`AuditLog`, or add a focused table for tool name, status, connector, actor and trace.

04

Lifecycle fields

Add `status`, `slug`, `deletedAt`, `lastActiveAt` style fields where Divo needs stronger tenant/user lifecycle control.

Important. These are additive. We do not need to delete the existing Divo schema to make Hermes work. We need a clean bridge and a few first-class columns/tables.

Phased transformation
1
DB intersection RFC start here
Finalize exact table mapping and additive schema names before more code moves. This is the decision document.
2
Postgres bridge vertical slice
One Hermes gateway/API request dual-writes to Divo `RuntimeConversation`, `RuntimeConversationMessage`, `RuntimeRun`, and `ExecutionRun` while SQLite still works.
3
Identity source of truth
Replace local company identity authority with Divo Postgres lookup. Every entrypoint resolves company/user/channel identity first.
4
Tool context and connector ownership
Every Hermes tool receives `companyId`, chooses company-owned credentials, and writes trace/audit rows.
5
Policy and cutover
Turn on RBAC/approval enforcement and make Postgres reads canonical for resume, history, admin UI and reporting.

What we do next

DB-first
1Write the schema RFC. Name the tables/fields and map Hermes SQLite columns to Divo Postgres models.
2Review with the tools agent. Make sure Zoho/Google/Lark connector ownership fits the same company model.
3Implement one bridge path. Start with one gateway/API message, not all channels at once.
4Prove no split-brain. Tests must show SQLite and Postgres receive the same ordered session/message/run data during bridge mode.

What we deliberately do not do first

  • Do not port all tools before company identity is canonical.
  • Do not create a second production Postgres service for Hermes.
  • Do not enforce RBAC before the audit/identity trail exists.
  • Do not scatter direct Postgres writes across Hermes. Keep a single bridge module.
Recommendation. The next engineering artifact should be a schema/bridge RFC, then one tested vertical slice. That keeps the transformation understandable and reversible.
