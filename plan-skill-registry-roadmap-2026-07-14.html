Project roadmap · 14 July 2026

Make company skills cloud-owned, searchable, and auditable.

Build the Skill Registry around the existing backend gateway. First remove local company-skill resolution; then make backend search, versioning, RBAC, and the admin library reliable before adding visual polish or semantic search.

Audience: Divo product and engineering team · Source: architecture review of the current workspace

Recommendation

Start with control, not the file browser.

The first delivery must ensure that only backend-approved skills can influence Divo Dex company work. The registry UI then becomes the safe control plane for those skills. Tool authorization and approvals remain backend decisions throughout.

Phase 0 — Lock the boundary

Goal: Divo Dex cannot select an arbitrary local company skill. Done when: a backend outage produces a safe unavailable response, every company skill fetch is audit logged, and an archive/revoke is visible within minutes.

Action plan

1. Set policy

  • Write one policy: “company skills are cloud-only.”
  • Decide whether personal local skills are allowed outside company mode.
  • Define who may draft, review, publish, archive, and restore.

2. Fix desktop routing

  • Make skills.search the first and only company retrieval path.
  • Disable local skill scanning and local fallback in company mode.
  • Stop passing writable user skill folders to Pi for company skill selection.

3. Harden gateway

  • Return skill ID, immutable version, and registry revision.
  • Audit searches, reads, denials, and tool invocations.
  • Cache only small discovery summaries for 1–5 minutes.

4. Evolve data safely

  • Add logical folders; do not create physical desktop folders.
  • Add immutable skill versions and published pointer.
  • Use required vs optional tool/action bindings.

5. Build admin library

  • Three panes: tree, contents, editor/preview.
  • Add draft, review, publish, archive, restore, and move.
  • Show scope, tool requirements, owner, version, and audit history.

6. Prove scale

  • Add PostgreSQL full-text search and a GIN index.
  • Benchmark 10k then 100k synthetic skills.
  • Measure p95 search, DB CPU, index size, and gateway latency before resizing VPS.

Build order and ownership

  1. Backend: policy flag, cloud-only resolver contract, audit events, version-aware response, focused gateway tests.
  2. Desktop: remove company-mode local-skill eligibility; preserve only the thin bundled gateway extension.
  3. Backend: folder/revision migration, registry endpoints, SQL full-text query.
  4. Admin: registry page using existing React, Tailwind, Radix, TanStack Query, and Lucide.
  5. Platform: VPS metrics and benchmark gate; defer vector search until search-quality evidence justifies it.

Dependency choices

V1 UI

Use existing admin dependencies. A simple accessible nested list is enough while product rules settle.

Large tree later

Use react-arborist only when virtualized large-tree browsing and drag/drop are truly needed. Do not add a second drag library.

Search

Use Postgres full-text search and GIN first. No new database or vector dependency is required for the first scalable release.

Risks to actively manage

Local skill removal can change existing personal workflows.

Mitigation: make the company-mode exception explicit and test both modes before removal.

Instructions are not enforcement.

Mitigation: backend remains the single authority for RBAC, approvals, and SaaS credentials.

VPS capacity is not yet measured.

Mitigation: benchmark the real query path before promising a capacity number or moving infrastructure.

Definition of success

An admin can create a folder, draft and publish a versioned skill, attach required tools/actions and a department scope, see who used it, revoke it, and have Divo Dex stop offering it within minutes. Pi never decides that a local company skill is allowed.
