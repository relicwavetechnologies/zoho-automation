Decision review · 17 July 2026

Keep the one-button demonstration. Replace “record everything” with governed evidence capture.

The user experience is directionally right for low-training company users. The proposed internals are not: continuous full monitoring, raw-video model ingestion, and self-editing live skills would create unnecessary privacy, cost, reliability, and authority failures.

Findings

Severity reflects production impact if the original proposal is implemented directly. Positives identify Divo components that should be reused instead of duplicated.

Critical

“Monitor everything” is the wrong data contract

Proposal + GDPR Art. 5 + DPDP Rules 2025

Full video, all URLs, system audio, and app history inevitably collect passwords, private messages, customer data, third-party conversations, and unrelated work. Consent alone does not make unlimited collection safe or proportionate.

Required change: session-scoped capture with a visible recording indicator, pause/stop, selected display/window, excluded apps/domains, no incognito/password-manager/auth windows, no keystrokes/clipboard, domain-only browser metadata by default, and short raw-artifact retention.
Critical

An AI must not directly rewrite an active company skill

skill-publishing.tool.ts:162–177 · skill-registry-versioning.ts:29–59

The current agent-facing publishing tool creates a new skill and rejects duplicate slugs; department admin updates mutate the live skill. There is no candidate-revision approval or rollback route. Automatic live edits would bypass the intended company/department authority boundary.

Required change: feedback creates a proposed patch against a pinned skill revision. The author can approve a personal draft; department/company changes require manager/admin publish. Keep immutable versions and add explicit rollback.
Warning

DeepSeek V4 Pro is a compiler here, not the vision pipeline

DeepSeek Chat Completion schema · media-ocr.service.ts:9–68

DeepSeek officially supports V4 Pro, max reasoning, JSON output, and tools, but the current API schema accepts text message content. Raw screenshots cannot be the direct model input.

Design: keyframes go through a vision/OCR stage; audio goes through speech-to-text; DeepSeek receives a compact, timestamped, structured timeline plus tool/skill/policy snapshots. Validate JSON because the provider notes occasional empty JSON output.
Warning

The existing OCR route is a single-image helper, not a recording processor

gateway.types.ts:3–16 · media-ocr.service.ts:9–15

media.image_ocr accepts one inline image with a 1.25 MB decoded cap. It has useful secret redaction and labels observations as untrusted, but no queue, artifact lifecycle, session RBAC, frame deduplication, or batch budget.

Design: reuse the extractor behind an asynchronous media pipeline. Add capture-specific authorization, object storage, checksums, deduplication, retries, backpressure, and per-session cost ceilings.
Warning

Current scheduling is time-only and prompt-driven

schedule-config.ts:12–41 · schedule-task.tool.ts:59–75 · scheduled-workflow.service.ts:182–235

The scheduler supports one-time/hourly/daily/weekly/monthly triggers and executes a compiled free-form prompt through the Lark engine. Rich workflow fields exist but are currently written as empty objects. This is insufficient for reliable event-triggered learned workflows.

Design: separate a versioned workflow definition from trigger bindings. Start with manual trigger, then reuse the existing scheduler as a schedule trigger adapter. Provider events and polling conditions come later.
Warning

Skill tool IDs are too coarse for learned automation

schema.prisma:938–951 · skill-catalog.service.ts:149–165

Runtime visibility currently requires every Skill.toolIds entry to be permitted. Action-level SkillCapability metadata exists, but its own comment says the write UI is not live and toolIds remains the enforced list.

Design: each compiled workflow step must pin toolId, action group, operation/schema revision, input mapping, output mapping, and approval policy. Do not infer write authority from skill prose.
Warning

Pro Max is not the current default and cost accounting needs verification

runtime.rs:24–26,190–196 · llm-proxy.service.ts:48–80 · pricing.ts:21–24

Jan company mode defaults to V4 Flash with medium thinking; the backend proxy defaults members to Flash-only. Pro must be explicitly granted. Also, the repository's Pro prices differ from the currently published DeepSeek pricing page, so budget decisions may be overstated.

Design: run compilation as a backend workload identity (workflow.compiler) with company budgets, explicit deepseek-v4-pro, thinking enabled, reasoning_effort=max, and updated pricing tests. Do not depend on a desktop member's chat model preference.
Suggestion

Make narration a push-to-explain affordance before continuous audio

Deepgram pre-recorded + utterance documentation

Short voice notes attached to marked steps produce better intent evidence with less unrelated speech and much lower privacy exposure. Continuous microphone and system-audio capture can remain an opt-in later.

V1: “Mark step” + “Explain what I’m doing” voice note. If long recordings are added, chunk audio asynchronously; Deepgram documents timeouts for long synchronous pre-recorded requests.
Positive

The backend already owns the correct company boundary

gateway-dispatcher.ts:47–64 · tool-executor.ts:186–309

Tool discovery, input validation, permission resolution, preflight, execution, audit, and approval are already backend-owned. The new compiler should consume these contracts and never reproduce RBAC or credentials in Jan/Pi.

Positive

HITL primitives already support exact-action review

local-approval-intent.service.ts:168–319 · tool-executor.ts:120–177

Local approval intents bind exact validated arguments to a session, expire, and are revalidated before commit. Manager approval can then gate department actions. Reuse this for workflow execution rather than inventing workflow-specific approval logic.

Positive

Versions, registry revisions, traces, and tool readiness already exist

schema.prisma:902–960 · trace-ingest.routes.ts:45–84 · gateway-dispatcher.ts:477–505

Immutable skill snapshots, company registry revisions, desktop execution traces, and side-effect-free tool preflight significantly reduce the amount of new platform work. The new pipeline should link to these records instead of storing opaque model output.

The recording is evidence, the workflow specification is the executable truth, and the skill is the human-readable recipe. They are related records—not one blob.

Backend workflow runtime

Device capture plane Local-first

  • OS capture permission and system picker; visible red indicator at all times.
  • Keep full raw video locally and ephemeral, or avoid generating it in V1.
  • Upload only selected/deduplicated keyframes and explicit voice notes.
  • Browser companion sends domain/title events only while a recording session is active.

Workflow learning plane New backend subsystem

  • WorkflowCaptureSession, ordered observations, artifact references, consent version, retention deadline.
  • Asynchronous OCR/STT jobs produce timestamped observations; raw media is never trusted as instructions.
  • Compiler sees current tool schemas, visible skills, connections, RBAC, and registry revision.
  • Web research runs only for capability gaps and produces proposed integrations—never grants or installs them.

Control and publishing plane Reuse existing authority

  • WorkflowDraft contains steps, branches, inputs, outputs, tool/action bindings, trigger candidates, uncertainty, and risk.
  • Confirmation edits the draft; preflight checks each proposed tool invocation/readiness where concrete arguments exist.
  • Publish creates a versioned workflow and a candidate skill revision. Scope decides who must approve.
  • Every run pins workflow version, skill revision, registry revision, connection, and trigger revision.

Phased implementation

Mock contract

All eight UI states, fake timeline, draft edits, trigger choice, test result, correction patch.

Exit: 5–10 target users can teach and confirm a workflow without training.

Capture spike

macOS ScreenCaptureKit and Windows Graphics Capture proof; app focus; sparse keyframes; explicit voice notes; local deletion.

Exit: 20-minute session stays bounded and excludes configured sensitive apps.

Analysis pipeline

Capture session records, object storage, queue, OCR/STT adapters, DeepSeek structured compiler, uncertainty questions.

Exit: a replayable fixture produces a schema-valid draft with linked evidence.

Governed publish

Tool/skill inventory snapshot, action-level bindings, connection readiness, confirmation, draft revision, admin approval.

Exit: no workflow can publish or execute with missing permissions/scopes.

Manual execution

Version-pinned run, preflight, local/manager HITL, traces, expected-output validators, step feedback.

Exit: corrections create a reviewable patch and rollback is tested.

Triggers

Schedule adapter first; then provider webhooks and bounded polling. No invisible always-on desktop monitoring.

Exit: duplicate delivery, retry, idempotency, and trigger disable paths are proven.
Recommendation

Build the teaching experience now; delay raw video infrastructure.

For the first functional slice, make the UI feel like screen recording while capturing a sparse, explainable evidence stream. Use manual trigger and explicit approval. Only add continuous video upload if real user tests show that sparse screenshots + marked voice notes cannot reconstruct workflows accurately.
